# PetVerse V10.2 UI production pass

## Purpose

V10.2 turns the V10 feature-complete interface into a readable, consistent
720×1280 mobile layout without changing gameplay, server contracts, data, or
existing button behavior.

The protected V10 baseline remains available separately. All V10.2 work is
isolated on `v10.2/ui-production-pass`.

## Global layout contract

- Design canvas: `720 × 1280`
- Fixed top status bar: `112`
- Fixed bottom navigation: `190`
- Safe horizontal margin: `24`
- Safe vertical inset inside the feature viewport: `16`
- Module gap: `16`
- Small gap: `8`
- Large card radius: `24`
- Small card radius: `16`
- Primary action height: `72`
- Secondary action height: `56`
- Normal list item height: `88–104`

Normal pages render below `TopBar` and above `BottomNavigation`. Only modal,
loading, reconnect, guide, reveal, and battle layers may cover those fixed
areas. A hidden overlay must never intercept input.

## Page decisions

### Home

- The pet remains the main visual focus.
- One dynamic primary action appears above navigation:
  - collect a ready hatchling; or
  - continue the main adventure.
- The pet, nameplate, title, and fixed navigation use one center line.
- The hand-painted navigation keeps its natural height instead of being
  vertically compressed.

### Pet

- The roster and detail column have distinct borders and a fixed gap.
- Roster cards are wider and separated by 12 pixels.
- Profile, tabs, detail, actions, and filters follow a 16-pixel vertical rhythm.
- Detailed data is split into attributes, skills, aptitudes, and equipment.
- Primary actions are separated from favorite, lineage, and lock utilities.

### Adventure, team, and formation

- World progress and team shortcuts no longer overlap.
- The story progress footer remains above the fixed navigation.
- Region actions explain why they are unavailable.
- Team editing retains one formation field, one scrollable pet list, and one
  save action within the safe viewport.

### Shop

- Products use a two-column `250 × 154` grid.
- Product cards use cream faces, clear outlines, visible item art/icon wells,
  owned count, price, sold-out state, and insufficient-currency state.
- Skill books have a secondary role filter.
- Empty categories provide an explanation and a refresh action.
- The list has bottom padding and an explicit end marker.

### More

- The black test-menu background is removed.
- Features are grouped by player intent:
  - pet nurture;
  - social interaction;
  - rewards and competition;
  - personal settings.
- Social features use two columns to reduce density.
- The duplicate page title inside the content area is removed.

### Inventory

- Items use a four-column `150 × 134` grid.
- Cards contain only the icon, name, category, and quantity/equipment state.
- The target pet, category tabs, item grid, and footer are separate modules.
- Empty categories explain where the relevant item type can be obtained.

### Hatchery

- The page is a nursery scene first, not a permanently open database grid.
- Three equal nursery nests occupy the main stage.
- The egg warehouse is an expandable drawer.
- The expanded warehouse uses four columns with filter and sorting controls.
- Empty filters can return to all eggs; an empty account can go to marriage or
  return home.

### Skills

- The page uses the same safe-area shell as other production pages.
- Current skills and skill books use balanced left/right columns.
- Empty columns explain the next step instead of leaving a blank panel.
- The learn action stays in a fixed description panel and explains disabled
  conditions.

### Fusion

- Father and mother cards are equal and symmetrical.
- The flow is shown as choose parents → review range → confirm fusion.
- Result range, materials, optional mutation essence, primary action, and risk
  copy are separated.
- The primary action explains which parent is still missing.

## State language

Disabled controls use warm neutral colors rather than generic grey. Important
actions can display a short reason such as “需要完整五宠编队” or “请先选择技能
书”. Empty states contain:

1. a recognizable icon;
2. a plain-language title;
3. a short explanation;
4. a relevant next action when one exists.

## Editor ownership

The user may continue adjusting editor-owned static art, transforms, typography,
and spacing. Runtime code may update data, active state, and dynamic lists, but
must not reposition or destroy editor-owned fixed UI.
